# HealthSys security and privacy

## Authentication and roles

- Staff passwords are validated and hashed on the server with bcrypt/bcryptjs. Passwords are not returned to views or written to application logs.
- Login regenerates the session ID. Authenticated requests re-read account status, role, and `session_version`; disabling an account, changing its role, or changing/resetting its password increments the version to invalidate prior sessions.
- Sessions expire after eight hours. Cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` when `NODE_ENV=production`.
- Patient pages and mutations require a valid session. Patient creation/visits/edits require an active clinical role; patient deletion/restoration and staff/report actions are administrator-only. The `/sync` route applies those restrictions to individual operations too.
- The `x-test-user` authentication exception is enabled only when both `NODE_ENV=test` and `HEALTHSYS_TEST_AUTH_BYPASS=true`. Production requests cannot use this header to bypass stale-session or disabled-account checks.
- Logout is a CSRF-protected POST. It destroys the server session, clears local patient snapshots and sync-status metadata, and leaves pending sync operations intact.
- Admin-only server backup, restore, and CSV import routes re-check the active Admin session and CSRF token on the server; staff cannot access them by calling the endpoints directly.

## HTTPS deployment

In production, set `NODE_ENV=production`, `HTTPS_REDIRECT_ORIGIN=https://your-public-host`, and configure `TRUST_PROXY` to the exact trusted proxy hop count or trusted proxy address/subnet when TLS terminates at a reverse proxy. The app redirects unencrypted requests to the configured HTTPS origin and only honors forwarded protocol information from configured proxies. Do not set `TRUST_PROXY=true` unless every proxy hop is trusted.

Production deployments must terminate TLS at a trusted reverse proxy/load balancer. The app's development certificates and HTTPS listener are not used in production. Keep session secrets, database credentials, and TLS private keys out of source control; `.env` and `server/cert/*-key.pem` are ignored by Git.

## CSRF and request limits

Cookie-authenticated state-changing requests use a session-bound CSRF token. Login is CSRF-protected as well. Login permits 10 attempts per client IP per 15 minutes; other state-changing routes permit 60 requests per IP per 15 minutes. Limits use an in-process memory store: they reset on restart and are not shared across multiple application instances. For multi-instance production deployments, replace the in-memory limiter with a shared Redis or gateway-backed limiter.

## Audit trail

Patient creates, updates, deletes, restores, visits, CSV imports/exports, and profile access are recorded in `patient_activity` and/or `security_audit_log`. Login outcomes, logout, staff account/role/password changes, and sync-batch outcomes are recorded in `security_audit_log`. Successful patient/staff mutations and server backup/restore audit entries commit in the same database transaction as their mutation. Entries contain actor/target IDs, action, outcome, timestamps, and limited metadata such as changed field names or dataset counts—not clinical notes, password values, or changed clinical values. Administrators can search and page through the audit history from Data Recovery; ordinary users cannot read or alter it.

CSV import is Admin-only, online, size-limited, validated as an all-or-nothing operation, and never overwrites existing patient records. Duplicate patient IDs are rejected; exact normalized phone matches are flagged for manual review. CSV exports honor the current filters across all result pages, and exports including deleted records are Admin-only. Exported cells are escaped against spreadsheet formula execution. Server backups include patient activity and security audit metadata; older backups without the optional audit fields remain supported.

Apply the audit and sync-history schema migrations after taking a TiDB Cloud snapshot/backup:

```powershell
npm run migrate:security-audit
npm run migrate:sync-logs
npm run migrate:patients
```

These additive migrations create their tables if absent or add missing columns/indexes; they do not modify or delete existing patient or staff records. Run them before deploying code that writes or displays the new audit/activity metadata.

## Offline data and limitations

- IndexedDB stores patient snapshots/fields needed by the patient interface (identity, demographics, contact details, emergency contact, clinical notes, status/version/timestamps), cached dashboard metrics, and pending patient operations. Pending operations are associated with the authenticated user's ID. Older queue entries without an owner are marked for review and are not synchronized automatically.
- `localStorage` stores sync-state metadata (attempt/success timestamps, outcome, short error summary) and the `healthsys:offline-access:v1` context (account ID, role, and verification/expiry times); it does not contain passwords or server session tokens. The offline context expires eight hours after its last server verification and is cleared when the server confirms an unauthenticated 401. Timeouts and temporary server errors do not prove session expiry and do not clear the context.
- Cache Storage contains versioned static application assets, a generic offline page, and the offline patient workspace and shared offline portal with their scripts/styles. Login responses, authenticated HTML, patient profiles, and patient JSON/API responses are not cached. When the network is unavailable, or Dashboard, Staff, Reports, or Data Recovery returns a server error (HTTP 5xx), navigation serves a static portal that reads only the previously authorized account's local data; it does not cache or replay server-rendered pages. Other private routes retain the generic fallback.
- The offline patient workspace supports local patient creation and edits for clinical staff and administrator accounts, and queues administrator-requested deletions as tombstones. It writes through the existing IndexedDB patient store and `syncQueue`; it does not create a second queue or report a server save before acknowledgment. On reconnection it verifies the current server session and only then runs the existing synchronization flow.
- The offline Dashboard derives clearly labeled device-local patient counts and queue status from IndexedDB and shows server metrics only from a timestamped, account-scoped snapshot. Reports can show a partial local summary of the stored patient snapshot; they do not apply URL date filters or imply database-wide completeness. Staff accounts are not stored locally, so the offline Staff page explains that directory and mutations require a connection. Data Recovery likewise explains that backup import/export requires the authenticated online page. These pages do not add a local staff store or another synchronization queue.
- Logout clears local patient snapshots and sync metadata but intentionally preserves queued operations. Those operations remain associated with their original account and are not sent under another account. Pending queue payloads can contain patient information and remain readable to someone with access to the browser profile/device.
- The dashboard can export/import a versioned local offline JSON file containing that account's cached patient snapshots and queued patient operations. Imports require the same account ID and merge without replacing existing patient rows or operation IDs. This file is sensitive, is not encrypted, and remains separate from server backups.
- A failed or interrupted IndexedDB open/migration is surfaced to the user. The application does not delete or recreate the database automatically. The v4 queue migration now marks unsupported legacy operations for review rather than deleting them; unsupported operation payloads are omitted from local exports/imports because they may contain credentials. Entries deleted by an older already-applied v4 migration cannot be recovered by this change.
- IndexedDB, Cache Storage, and the browser-local offline context are not encrypted or cryptographically protected by this application. Browser storage is not protected from someone with access to the unlocked device/browser profile, developer tools, or script running in the origin. Use managed devices, OS disk encryption, screen locks, and browser-profile controls. Offline access is a usability boundary for an established browser profile, not protection against a person who controls that profile.
- Offline state is not proof of current server authorization. The local context is available for up to eight hours after a successful server verification; a server-confirmed 401 invalidates it. A session/account revoked while the browser is disconnected cannot be detected until connectivity returns or the context expires. Server-side session and role checks remain authoritative for every server operation.
- Patient sync uses optimistic record-version checks: EDIT and DELETE requests include the version from the client snapshot, and the server atomically updates only when the stored version still matches and the patient is active. A stale operation is returned as an unresolved `version_mismatch`; the client retains it for review. The conflict review preserves the original, local, and current server snapshots; users may select values field by field or explicitly keep the entire queued record. Only after that explicit choice is a new operation queued against the server version, and its update is still checked atomically. Independent duplicate soft-deletes are acknowledged idempotently without creating duplicate activity.
- Patient snapshots have no time-to-live; they remain in IndexedDB until logout clears them, an account switch removes the prior user's snapshots, or the browser/device removes site data. Pending/failed queue operations have no automatic expiry and remain until the server confirms them or local browser data is explicitly removed. Session expiry or account disablement blocks server requests but cannot remotely purge disconnected device storage. The app warns on logout when pending/review-required operations are present, but cannot intercept a user clearing site data from browser settings; export a local offline backup first.

## PWA installation, offline use, and updates

- `/manifest.json` defines the standalone app and references the square 192px and 512px HealthSys PNG icons. The app must be served from HTTPS (or localhost for development) to install and use the service worker.
- The service worker uses a release-named `healthsys-*` cache. It caches a bounded static shell, pins static assets to the active worker's cache, and removes only obsolete HealthSys caches after activation. Authenticated HTML and API responses are network-only.
- The initial worker install does not force activation. When an update is waiting, the page offers **Update now** or **Later**. Before activation it checks connected tabs for active IndexedDB writes, database opening/migration, and synchronization. It asks for explicit confirmation if this account has queued or failed operations. Activation/reload does not clear IndexedDB or the sync queue; queued operations remain unconfirmed until the server acknowledges them.
- Offline patient workspace support is intentionally limited: it lists records already stored for the previous account on that device and permits supported patient changes in the existing local queue. The static workspace and portal are not authenticated server sessions and cannot perform protected server operations; queued changes require a freshly verified session before synchronizing after reconnecting. Offline Dashboard/Reports values are labeled as local or stale snapshots, and Staff records are not available offline. Appointment management is online-only; appointments are not stored or queued in IndexedDB and must not be treated as confirmed while offline.

## Appointment management

- Run `npm run migrate` before deploying the appointment UI. Migration `006_appointments` adds the `appointments` and append-only `appointment_events` tables; it does not drop or reset existing data. It adds patient/staff foreign keys when the deployed parent tables use compatible UUID columns and InnoDB. Appointment changes and their security-audit records are committed in one transaction.
- Appointment times are entered and displayed as UTC, including the calendar date, and stored in a UTC `DATETIME`. This avoids interpreting ambiguous/nonexistent local wall times across timezone or daylight-saving changes. Durations are 5–240 minutes in five-minute increments, and booking intervals use a half-open `[start, end)` boundary.
- A scheduling transaction locks the assigned staff row before checking active overlaps and inserting/rescheduling, serializing simultaneous booking attempts for that staff resource. Only scheduled appointments block slots; cancellation changes status and appends a history event rather than deleting records. Appointment history and operation IDs are included in server backups; older backup files without appointment datasets remain restorable.
- Appointment management requires a current online authenticated session. Staff can only schedule for themselves and list/change appointments assigned to themselves; Admins can assign active staff and manage all appointments. Appointments are deliberately not added to the patient IndexedDB or patient synchronization queue.
- To install, first open the HealthSys HTTPS deployment online, then use the browser's **Install app** / **Add to Home Screen** prompt or menu. To manually verify offline use, load the Patient Management page once, disconnect the network, open `/patients`, and confirm only locally stored records appear. Add a synthetic patient, reload while offline, then reconnect and sign in to verify the operation is acknowledged. A server-side backup does not include the pending local operation.
- To verify an update, with a synthetic patient operation pending, deploy a new version with a bumped `CACHE_NAME`, open the app and choose **Update now**. Confirm pending-change warning, reload, ensure the local record and queue remain, then sign in and synchronize. Updates are served only after the new worker's required shell has cached successfully.
- Unit tests simulate cache/install/navigation and worker lifecycle behavior. Real browser installation, HTTPS deployment, browser restart persistence, and device-specific offline/update behavior still require manual testing; a VM service-worker test is not a substitute for those checks.

## Verification and known limits

Run `npm test` (or `npm run test:unit`) for the deterministic Node.js regression suite. It uses synthetic/in-memory data and includes synchronization failure/retry, local transaction rollback on storage errors, authentication rejection, queue preservation, and service-worker fallback tests; it does not require a database. Database integration tests are separate: only after confirming a dedicated disposable database, configure `.env` so `DB_NAME` contains `test`, `testing`, or `ci`, and explicitly set `ALLOW_DESTRUCTIVE_INTEGRATION_TESTS=true` in the test process before running `npm run test:integration`. The integration guard fails closed without both safeguards. Never use production or real patient data. `npm run test:release` runs unit tests followed by these guarded integration tests, which include injected server transaction rollback and database-backed CRUD, auth/role, operation idempotency, stale-version rejection, concurrent same-version updates, and two-client conflict scenarios. The harness uses independent synthetic identities but is not a real multi-browser test. Production proxy topology, shared multi-instance rate limiting, browser/device storage behavior, and backup restoration must be verified in the deployment environment.

## CSV export/import and server backup recovery

- Any authenticated clinical user can download active patient CSV records from the Patient Management page. Admins can explicitly request deleted rows. The CSV allowlist contains patient ID, demographic/contact and clinical fields, soft-delete/version status, and creation/update timestamps; it excludes staff passwords, session data, and security secrets. CSV values are quoted, formula-leading text is neutralized, and export reads in database batches.
- CSV import is Admin-only at `/admin/recovery`. The preview validates headers, patient fields, duplicate IDs, and row shape. No rows are committed if any row is invalid or duplicates an existing patient ID. Successful imports use one database transaction and create new active records; they do not restore visit/activity history or archived state.
- The Admin recovery page downloads a streamed `healthsys-server-backup` JSON file, version 1/schema version 1. It contains patients, visits, patient activity, safe staff metadata (not password hashes), security audit events, sync idempotency records, and synchronization history. Backup creation is explicitly confirmed and responses are marked `no-store`. Files include sensitive clinical and audit information; store them only in access-controlled encrypted storage. The restore upload is capped at 50 MB and 100,000 total rows.
- Server backups do not contain IndexedDB data or changes that have not synchronized. Export a separate local offline backup from the dashboard before device/browser repair or other local recovery. Local files are not encrypted.
- Restore never overwrites a populated database. It is allowed only in a freshly prepared database with exactly one active, non-deleted bootstrap Admin account and no patients, visits, patient activity, sync history, or sync idempotency records. The Admin must preview the target and type `RESTORE`; all inserts run in a transaction. Existing security audit events are retained, then backed-up audit events are appended.
- Backups intentionally omit all password hashes. Before restoring, configure `RESTORE_ADMIN_PASSWORD` as a strong password satisfying the normal staff password policy. After restore, sign in as the active Admin username shown in the preview using that configured password, then reset every other restored staff account through Staff Management; those accounts receive unusable random hashes. Remove `RESTORE_ADMIN_PASSWORD` from the runtime environment after the recovery.

### Safe server restore procedure

1. Take and verify a TiDB Cloud snapshot/backup before changing deployment databases. Never test restoration on the production database.
2. Provision a separate, empty test/fresh database. Deploy compatible HealthSys code and apply its patient-management, staff-security, security-audit, sync-idempotency, and sync-history migrations. Create exactly one temporary active Admin account; do not seed patients or additional staff.
3. Set `RESTORE_ADMIN_PASSWORD` in the server environment to a strong temporary password and restart the application.
4. Sign in to the fresh environment, open **Data recovery**, upload the backup JSON, and validate the file and target. Continue only if the target is confirmed fresh and the counts/administrator are expected.
5. Type `RESTORE` at the final confirmation. On success, sign in again with the backup's active Admin username and `RESTORE_ADMIN_PASSWORD`. Reset other restored staff credentials and remove the temporary environment variable.
6. Verify patient, visit, activity, staff, audit, and sync-operation counts and representative relationships/timestamps in the separate test database before using the same process for a production recovery.

This repository's automated recovery tests use synthetic data for CSV parsing/validation, backup structure/relationship validation, local offline queue export/import, and IndexedDB-open failure handling. They do not prove server CSV transaction behavior or backup restoration against TiDB; run those only against a separately verified disposable test database. No backup/restore integration test has been run against the currently configured database.
